# Tezca protocol v1

Normative reference for the server (`/server`) and the plugin (`/plugin`). The schema is in
[`proto/tezca/v1/sync.proto`](../proto/tezca/v1/sync.proto). `PROTOCOL_VERSION = 1`.

## Trust model

The host is **honest-but-curious storage**. It authenticates users by Ed25519 signatures, enforces
roles, assigns sequence numbers, and stores and relays bytes. It never holds a decryption key.
It can see: user public keys, space and doc IDs, sizes, timing, and who wrote what.
It cannot see: paths, file names, content, cursors, or space names.

(Known M1 limitation: a malicious host could lie about space membership lists. Signed membership
logs are planned for M3.)

## Encodings

- `b64u`: base64url without padding.
- **IDs**: `space_id` and `doc_id` are 16 random bytes in `b64u` form (22 chars), generated by
  the client. The reserved doc id `index` is a space's index document.
- **User identity**: `sign_pk` (Ed25519, 32 bytes) is the user ID. `box_pk` (X25519, 32 bytes) is
  used for key wrapping. Both are derived from one 32-byte identity seed:
  - `sign_seed = BLAKE2b-256(key = seed, msg = "tezca/v1/identity/sign")` →
    `crypto_sign_seed_keypair`
  - `box_seed = BLAKE2b-256(key = seed, msg = "tezca/v1/identity/box")` →
    `crypto_box_seed_keypair`
  - The recovery phrase is the BIP-39 English mnemonic of `seed` (24 words).

### sigInput

Every signature and every AEAD associated-data value is built with one canonical function:

```
sigInput(purpose, f1, f2, …) =
    "tezca/v1/" ‖ purpose ‖ 0x00 ‖ for each field: u32be(len(f)) ‖ f
```

Strings are UTF-8 bytes. `u32(x)` is 4 bytes big-endian. `u64(x)` is 8 bytes big-endian.

| purpose | fields | used for |
|---|---|---|
| `auth` | server_id, nonce, sign_pk, device_id | WebSocket `Auth.sig` |
| `http` | method, path_with_query, u64(ts_unix_seconds), sha256(body) | HTTP `Authorization` |
| `redeem` | server_id, token, sign_pk, box_pk | `/api/claim`, `/api/redeem` |
| `update` | space_id, doc_id, u32(epoch), payload | `PushUpdate.sig` / `Update.sig` |
| `snapshot` | space_id, doc_id, u64(base_seq), u32(epoch), payload | `PutSnapshot.sig` |
| `ad-update` | space_id, doc_id, u32(epoch) | AEAD associated data for updates |
| `ad-snapshot` | space_id, doc_id, u32(epoch) | AEAD AD for snapshots |
| `ad-awareness` | space_id, doc_id, u32(epoch) | AEAD AD for awareness |
| `ad-meta` | space_id, u32(epoch) | AEAD AD for space metadata |
| `ad-pairing` | (none) | AEAD AD for pairing payloads |
| `ad-blob` | space_id, blob_id, u32(epoch) | AEAD AD for blobs |
| `ad-invite` | space_id, u32(epoch) | AEAD AD for a space key wrapped for a share invite |

Golden vectors are in `proto/vectors/sig-vectors.json`. They are generated by the plugin and
verified by both the Go and TS test suites.

### Encrypted payloads

`payload = nonce(24 random) ‖ crypto_aead_xchacha20poly1305_ietf_encrypt(plaintext, AD, nonce, key)`

- Space keys are 32 random bytes per epoch. They are wrapped per member as
  `crypto_box_seal(key, member.box_pk)`.
- **Update** plaintext: a Yjs update (v1 encoding).
- **Snapshot** plaintext: `Y.encodeStateAsUpdate(doc)`, covering every update with
  `seq ≤ base_seq`.
- **Awareness** plaintext: a `y-protocols/awareness` update.
- **Meta** plaintext: UTF-8 JSON `{"name": "...", "created": <unix ms>}`.
- **Blob** plaintext: the raw file bytes. `blob_id = b64u(BLAKE2b-256(key = blob_mac_key, msg = plaintext))`
  (43 chars) with `blob_mac_key = BLAKE2b-256(key = space_key[epoch], msg = "tezca/v1/blob-id")`.
  Keyed, so the host can't confirm guesses about content. Same file + same epoch ⇒ same id, so
  uploads are idempotent and deduplicated. The AEAD AD is `sigInput("ad-blob", space_id, blob_id, u32(epoch))`.

## HTTP API

The server speaks plain HTTP. TLS is the reverse proxy's job. `TEZCA_PUBLIC_URL` (optional) sets
the URL used in generated links. Otherwise the URL is taken from `X-Forwarded-Proto`/`Host`.

| Method & path | Auth | Body → Response |
|---|---|---|
| `GET /healthz` | none | `ok` |
| `GET /api/info` | none (optional HTTP sig) | `{server_id, protocol_version, claimed, name, max_blob_bytes, role?}` (`role` only for a valid signature, see M4) |
| `GET /` | none | Setup landing page. When unclaimed, it tells the operator to run `docker compose logs` to find the claim link. |
| `GET /invite` | none | Invite page for join and share links (see "Invite links"). Static: the invite is in the fragment, read by `/invite.js`. Its CSP allows only same-origin scripts (`/invite.js`, `/qrcode.js`); `Referrer-Policy: no-referrer`. |
| `GET /claim?code=…` | claim code | HTML page with the `obsidian://` claim link + QR code. 404 if the server is claimed or the code is wrong. |
| `POST /api/claim` | body sig | `{code, sign_pk, box_pk, sig}` → `{server_id, role:"admin"}`. One-time. `sig = sign(sigInput("redeem", server_id, code, sign_pk, box_pk))`. |
| `POST /api/invites` | HTTP sig, admin | `{role:"member", ttl_seconds?}` → `{token, expires_at, link}` |
| `GET /api/invites` | HTTP sig, admin | `{invites:[{token_hint, role, expires_at, redeemed_by}]}` |
| `POST /api/redeem` | body sig | `{token, sign_pk, box_pk, sig}` → `{server_id, role}`. Single-use. Re-redeeming with the same key is idempotent. |
| `GET /api/users` | HTTP sig, admin | `{users:[{sign_pk, box_pk, role, created_at}]}`, oldest first. `role` is `"admin"`, `"member"` or `"guest"`; `created_at` is unix seconds. |
| `DELETE /api/users/{sign_pk}` | HTTP sig, admin | `{}`. Removes a host user (see "Removing a user"). 404 unknown user, 409 if they're the last admin. |
| `PUT /api/spaces/{space_id}/blobs/{blob_id}` | HTTP sig, OWNER/EDITOR | Raw ciphertext body (`application/octet-stream`) → `{size}`. 201 if stored, 200 if it already existed (body discarded). 413 if larger than `max_blob_bytes + 40`. |
| `GET /api/spaces/{space_id}/blobs/{blob_id}` | HTTP sig, member | → raw ciphertext, or 404. |
| `HEAD /api/spaces/{space_id}/blobs/{blob_id}` | HTTP sig, member | 200 (with `Content-Length`) or 404. |
| `POST /api/pairings` | HTTP sig | `{ciphertext}` (b64u, ≤ 64 KiB) → `{id, expires_at}`. TTL 15 min. At most 5 unexpired pairings per user; more gets 429. |
| `GET /api/pairings/{id}` | none | `{ciphertext}` once, then 404 (deleted on read). |
| `GET /ws` | WS handshake below | WebSocket upgrade |

Cross-origin access: every `/api/*` response carries `Access-Control-Allow-Origin: *`,
`Access-Control-Allow-Headers: Authorization, Content-Type` and
`Access-Control-Allow-Methods: GET, POST, PUT, DELETE, HEAD, OPTIONS`, and `OPTIONS` preflights get `204`. `/ws` accepts
any `Origin` (Obsidian connects from `app://obsidian.md`, `capacitor://localhost`, …). Both are safe
because authentication is by signature, never by cookies.

HTTP errors return a JSON body `{"error": "..."}` with status 400 (bad input), 401 (bad, missing or
skewed signature, or unknown user), 403 (not admin, wrong claim code, or not a member of the space / not allowed to write), 404 (unknown invite or
pairing), 409 (already claimed, invite redeemed by another key, last owner, key set doesn't match, reused signature), 410 (invite expired or revoked),
413 (too large) or 429 (too many open pairings, or too many failed attempts; see "Rate limits").

Request bodies have read deadlines: a JSON body must arrive within 30 s, and a blob upload may take
as long as it keeps moving, but a pause of more than 60 s ends it. The connection is closed when a
deadline passes.

JSON byte fields are `b64u`. HTTP sig header:
`Authorization: Tezca pk=<b64u sign_pk>, ts=<unix seconds>, sig=<b64u>` with ±300 s skew allowed.
`path_with_query` is the request URI as sent, e.g. `/api/invites`.

Each signature on a state-changing request (anything but `GET`/`HEAD`, and except blob `PUT`s,
which are idempotent) is accepted once: the server remembers `(pk, ts, sig)` for as long as `ts`
is within the skew window and answers a repeat with 409 `duplicate request: sign it again with a
new timestamp`. Ed25519 signatures are deterministic, so a client that sends the same request twice
within one second must sign the second one with a later `ts`.

#### Removing a user

`DELETE /api/users/{sign_pk}` (`sign_pk` as b64u) lets an admin revoke a user's access to the host,
for example someone who left or an identity on a lost device. In one transaction the server deletes
the user, their memberships and wrapped keys in every space, their pairings, and the unredeemed
host and share invites they created. It then closes the user's live WebSocket sessions (status
1008, reason `user removed`) and sends `SpaceChanged` to the remaining members of each space they
were in. The spaces and everything written to them stay. A share whose only owner was removed keeps
its other members, but nobody can manage it any more. Owners should rotate the key of shares the
user was in, since they still hold the old epochs' keys. The last admin can't be removed, by anyone
including themselves. All of a user's devices share one identity, so this removes every device; the
person can rejoin with a new invite and a new identity.

Plugin deep links (handled by the plugin, not the server):
- `obsidian://tezca?do=claim&host=<url>&code=<code>`
- `obsidian://tezca?do=join&host=<url>&token=<token>`
- `obsidian://tezca?do=pair&host=<url>&id=<pairing id>&k=<b64u pairing secret>`
- `obsidian://tezca?do=share&host=<url>&token=<token>&k=<b64u secret>` (see "Share invites")

#### Invite links

Join and share invites are sent to people who may not have the plugin yet, so the link people
share is the host's invite page with the deep link's parameters in the URL fragment:
`<host url>/invite#<params>`, e.g. `https://sync.example.com/invite#do=join&host=…&token=…`.
Browsers never send the fragment to the server. The page's script reads it, and shows an
**Open in Obsidian** button for `obsidian://tezca?<params>`, setup steps, a QR code of the page's
own URL (drawn in the browser) and a copy-link fallback. It makes no requests with the fragment.
A host that serves a tampered page could read the fragment, so a share's `k` is only as safe as
the host serving its invite page; that's the same host that stores the share.

Clients accept either form wherever a link is pasted: an `obsidian://tezca?…` link's query, or an
`http(s)://…` link's fragment. Claim and pairing links stay `obsidian://` links.

## WebSocket session

1. Client connects to `/ws`. The server immediately sends `Challenge{nonce, server_id, protocol_version}`.
2. Client sends `Hello{sign_pk, device_id, protocol_version, client_version}`, then
   `Auth{sig}`. (Sending both back-to-back is allowed.)
3. If `protocol_version` differs, the server replies `Error{UPDATE_REQUIRED}` and closes. If the key
   isn't a registered user or the signature fails, it replies `Error{UNAUTHORIZED}` and closes.
   Otherwise it sends `AuthOk{sign_pk, box_pk, role}`.
4. Any other frame before `AuthOk` is rejected with `UNAUTHORIZED` and the connection is closed.

Limits before `AuthOk`: frames are capped at 4 KiB (a larger one closes the connection with status
1009), `device_id` at 64 bytes (longer is `UNAUTHORIZED`), and the client has 10 s from the upgrade
to authenticate. After `AuthOk` frames may be up to 17 MiB. The server caps concurrent WebSocket
connections in total (`TEZCA_MAX_CONNS`, default 1000; refused with HTTP 503) and per client
address (`TEZCA_MAX_CONNS_PER_IP`, default 50; refused with HTTP 429) before upgrading.

Request/response frames carry `rid` (requests) or `ref` (pushes). Errors echo it in `Error.rid`.

### Spaces

- `ListSpaces{rid}` → `SpaceList{rid, spaces}` returns every space the caller is a member of,
  including `keys` wrapped for the caller and the member list.
- `CreateSpace{rid, space_id, kind, wrapped_key, meta}` → `SpaceCreated{rid, space}`. The caller
  becomes `OWNER`, epoch 0. In M1 only hosts' admins/members may create spaces, and guests get
  `FORBIDDEN`. A duplicate id returns `CONFLICT`.

### Doc heads (space-level change feed)

- `SubscribeSpace{space_id}` requires membership. The server replies `DocHeads{full:true}` listing
  every doc in the space with `latest_seq > 0` or a snapshot. Afterwards, whenever any doc in that
  space gets a new seq or snapshot, every subscriber of the space gets
  `DocHeads{full:false, heads:[that doc]}`.
- This lets clients find docs that changed without subscribing to all of them.
- `UnsubscribeSpace` stops the feed.

### Doc sync

`Subscribe{space_id, doc_id, since_seq}` (membership required):
1. If the doc's latest snapshot has `base_seq > since_seq`, the server sends `Snapshot` first and
   then continues from `base_seq`. Otherwise it continues from `since_seq`.
2. The server sends `Updates` with every stored update where `seq > from` in ascending order,
   batched (≤ 256 updates or ~1 MiB per frame).
3. The server sends `SyncDone{latest_seq, updates_since_snapshot, bytes_since_snapshot}`.
4. From then on, the subscriber receives live `Updates` (usually one update each) for updates
   pushed by *other* connections.

Per connection and per doc, the server delivers updates in strictly ascending `seq` with no
gaps. Steps 1–3 and live delivery must not interleave out of order: the server takes the doc
lock, sends the backlog, and registers the subscriber atomically.

`Unsubscribe` stops live delivery. Subscribing to a doc with no history is fine: it returns
`SyncDone{latest_seq:0}`.

### Writes

`PushUpdate{ref, space_id, doc_id, epoch, payload, sig}`:
- Requires role `OWNER` or `EDITOR`. Otherwise the server returns `FORBIDDEN`.
- `epoch` must equal the space's current epoch. Otherwise the server returns `EPOCH_STALE`.
- `sig` must verify under the session's `sign_pk`. Otherwise the server returns `UNAUTHORIZED`.
- `len(payload) ≤ 4 MiB`. Otherwise the server returns `TOO_LARGE`.
- The doc is created implicitly on first write.
- The server assigns `seq = latest_seq + 1` and stores it durably (committed before the ack).
  It then replies `Ack{ref, space_id, doc_id, seq}` to the sender, broadcasts `Updates` to the
  doc's *other* subscribers, and sends `DocHeads{full:false}` to the space's subscribers.
- Order on the sender's connection: the Ack is sent after any earlier live updates for that doc,
  so the sender sees seqs in order.

`PutSnapshot{ref, space_id, doc_id, base_seq, epoch, payload, sig}`:
- Same role, epoch and signature checks, with `≤ 16 MiB`.
- `1 ≤ base_seq ≤ latest_seq`, and `base_seq` greater than the current snapshot's `base_seq`.
  Otherwise the server returns `CONFLICT`.
- The server stores the snapshot (with `created_at` = now) and applies retention (below): it keeps
  stored updates with `seq ≤ base_seq` for the history window rather than dropping them. It replies
  `SnapshotAck{…, created_at}` and sends `DocHeads{full:false}` to space subscribers.
- `SyncDone.snapshot_created_at` is the latest snapshot's `created_at` (0 if none).
- Clients should snapshot when `SyncDone.updates_since_snapshot > 500` or
  `bytes_since_snapshot > 1 MiB`, and only when they have no unacknowledged local updates for
  the doc.

### History

Retained snapshots are a doc's **versions**. Retention runs after every `PutSnapshot` for that doc:
- always keep the latest snapshot;
- keep the newest snapshot in each clock hour for the last `TEZCA_HISTORY_HOURS` (default 24) hours;
- keep the newest snapshot in each UTC day for the last `TEZCA_HISTORY_DAYS` (default 30) days;
- delete the rest.

The **update log** is kept for the same window: at each `PutSnapshot` the server deletes only updates
with `seq ≤ base_seq` stored more than `TEZCA_HISTORY_DAYS` ago. Each stored update records when it
arrived (`Update.created_at`, unix ms, set by the server). Servers that keep the log advertise
`"update-log"` in `/api/info` `features`, and answer
`GetUpdates{rid, space_id, doc_id, from_seq (exclusive), to_seq (inclusive, 0 = latest)}` with one
`UpdateRange{rid, …, updates, done}` holding a capped batch (≤ 2000 updates / 4 MiB); `done = false`
means ask again from the last seq. Clients rebuild any point in the window themselves (an earlier
snapshot, or the doc's start, plus the updates after it) and offer restore points at the end of each
burst of edits and just before any large deletion. Clients must not send `GetUpdates` to servers
without the feature (older servers answer unknown frames with an error that carries no `rid`).

Clients take a **version snapshot** (an ordinary `PutSnapshot`) when they have edited a doc locally,
all their updates are acked, and the latest snapshot is older than an hour; they wait for the doc to
be quiet for 30 s first.

- `ListVersions{rid, space_id, doc_id}` (membership) → `VersionList{rid, …, versions}` newest first,
  each `{base_seq, created_at, author, size, epoch}`.
- `GetVersion{rid, space_id, doc_id, base_seq}` (membership) → `VersionData{rid, …, info, payload, sig}`
  or `Error{NOT_FOUND}`. The payload decrypts exactly like a `Snapshot`.

Restoring a version is a new edit (the client diffs the current text to the old one), never a rewind.

### Awareness

`AwarenessIn{space_id, doc_id, epoch, payload}` requires membership (viewers may send presence).
It's relayed as `AwarenessOut{…, from, device_id}` to the doc's other subscribers. It's never
stored and is limited to 64 KiB.

### Keepalive

The client sends `Ping` every 25 s, and the server replies `Pong`. The server closes sessions idle
for more than 90 s.

## Server storage (SQLite, WAL)

```
server(k TEXT PRIMARY KEY, v BLOB)                       -- server_id, claim_code, name
users(sign_pk BLOB PRIMARY KEY, box_pk BLOB, role INT, created_at INT)
invites(token TEXT PRIMARY KEY, role INT, created_by BLOB, created_at INT, expires_at INT, redeemed_by BLOB, redeemed_at INT)
pairings(id TEXT PRIMARY KEY, owner BLOB, ciphertext BLOB, expires_at INT)
spaces(space_id TEXT PRIMARY KEY, kind INT, epoch INT, meta BLOB, meta_epoch INT, created_by BLOB, created_at INT)
members(space_id TEXT, sign_pk BLOB, role INT, PRIMARY KEY(space_id, sign_pk))
space_keys(space_id TEXT, epoch INT, sign_pk BLOB, wrapped BLOB, PRIMARY KEY(space_id, epoch, sign_pk))
docs(space_id TEXT, doc_id TEXT, latest_seq INT, snapshot_seq INT, updates_since_snapshot INT, bytes_since_snapshot INT, PRIMARY KEY(space_id, doc_id))
updates(space_id TEXT, doc_id TEXT, seq INT, epoch INT, author BLOB, payload BLOB, sig BLOB, PRIMARY KEY(space_id, doc_id, seq))
snapshots(space_id TEXT, doc_id TEXT, base_seq INT, epoch INT, author BLOB, payload BLOB, sig BLOB, created_at INT, PRIMARY KEY(space_id, doc_id, base_seq))
blobs(space_id TEXT, blob_id TEXT, size INT, created_by BLOB, created_at INT, PRIMARY KEY(space_id, blob_id))
```

Blob bytes live in a blob store, not SQLite:
- **Filesystem** (default): `$TEZCA_DATA_DIR/blobs/<space_id>/<blob_id[0:2]>/<blob_id>`, written to a
  temp file and renamed.
- **S3-compatible** when `TEZCA_S3_BUCKET` is set: `TEZCA_S3_ENDPOINT` (host[:port]),
  `TEZCA_S3_ACCESS_KEY`, `TEZCA_S3_SECRET_KEY`, `TEZCA_S3_REGION`, `TEZCA_S3_PREFIX` (optional),
  `TEZCA_S3_INSECURE=1` for plain HTTP. Key: `<prefix>blobs/<space_id>/<blob_id>`.

`TEZCA_MAX_BLOB_MB` (default 100) caps plaintext size. Blobs are never deleted by the server in M2
(it can't see which ones the encrypted index still references); client-driven GC comes later.

## Shares (M3)

A share is a space of kind `SHARE`. Any host ADMIN or MEMBER can create one (`CreateSpace`); the
creator is its OWNER. Guests (M4) can't create spaces.

### Share invites

The owner makes a single-use, expiring link. A random 32-byte `secret` travels only in the link
(`k=`). Each epoch key the invitee needs is wrapped for the link as
`nonce(24) ‖ xchacha20poly1305(space_key[epoch], AD = sigInput("ad-invite", space_id, u32(epoch)), key = BLAKE2b-256(key = secret, msg = "tezca/v1/share-invite"))`.

Link: `<host url>/invite#do=share&host=<url>&token=<token>&k=<b64u secret>` (see "Invite links"), which opens `obsidian://tezca?do=share&host=<url>&token=<token>&k=<b64u secret>`.

| Method & path | Auth | Body → Response |
|---|---|---|
| `POST /api/spaces/{space_id}/invites` | HTTP sig, OWNER | `{role: "editor"\|"viewer", keys: [{epoch, wrapped}], ttl_seconds?}` (default 7 days, max 30) → `{token, expires_at}`. `keys` must cover every epoch `0..current`. |
| `GET /api/spaces/{space_id}/invites` | HTTP sig, OWNER | `{invites: [{token, role, created_at, expires_at, redeemed_by?, redeemed_at?}]}` |
| `DELETE /api/spaces/{space_id}/invites/{token}` | HTTP sig, OWNER | → `{}`. Revokes an unredeemed invite (404 if unknown, 409 if already redeemed). |
| `POST /api/share-invites/redeem` | HTTP sig (the redeemer) | `{token}` → `{space_id, role, keys: [{epoch, wrapped}], kind, epoch, meta, meta_epoch}`. The caller must be a host user (401 otherwise). Single-use: 409 if redeemed by another key, 410 if expired or revoked; re-redeeming with the same key returns the same answer. Adds the caller as a member with the invite's role (an existing member keeps the higher role). |

After redeeming, the client unwraps the keys with `secret`, re-wraps each for its own `box_pk`
and uploads them, so its other devices receive them through `ListSpaces`:

| `PUT /api/spaces/{space_id}/keys` | HTTP sig, member | `{keys: [{epoch, wrapped}]}` → `{}`. Stores the caller's own wrapped keys (replacing any for the same epoch). Epochs must be `≤ current`. |

Details:
- A redeem's `role` is the caller's resulting role; `kind` is `"root"`, `"share"` or `"profile"`;
  `meta` is b64u; times are unix seconds. `ttl_seconds` is clamped to 1 minute … 30 days.
- Revoked invites answer redeem with 410 and are left out of `GET`; revoking twice is fine.
- Re-redeeming by the original redeemer works (even after expiry) only while they're still a
  member; after they leave or are removed the link answers 410, so it can't undo a removal.
- Rotating the key revokes pending invites (their keys stop at the old epoch).
- Key sets that don't match current state (invite epochs, rotation members) are 409; malformed
  ones (duplicates, empty or > 256-byte wrapped keys, a `PUT keys` epoch above current) are 400.

### Membership

| Method & path | Auth | Body → Response |
|---|---|---|
| `PUT /api/spaces/{space_id}/members/{sign_pk b64u}` | HTTP sig, OWNER | `{role: "owner"\|"editor"\|"viewer"}` → `{}`. 404 if not a member. Can't demote the last owner (409). |
| `DELETE /api/spaces/{space_id}/members/{sign_pk b64u}` | HTTP sig, OWNER, or the member themselves (leave) | → `{}`. Removes the member and their wrapped keys, and ends their subscriptions to the space and its docs. The last owner can't leave (409). |
| `POST /api/spaces/{space_id}/rotate` | HTTP sig, OWNER | `{epoch, keys: [{sign_pk, wrapped}]}` → `{epoch}`. `epoch` must be `current + 1` (409 otherwise) and `keys` must contain exactly one key for every current member. The server stores them and sets the space epoch. |

Each of these, and a redeem, pushes `SpaceChanged{space_id}` to the connected sessions of every
member (including one just removed). Writes under an older epoch then get `EPOCH_STALE`; clients
re-run `ListSpaces`, pick up the new key, and resend their pending updates under it. Old epochs'
keys stay with the remaining members, so history stays readable. A removed member keeps what they
already had but can't fetch anything new.

The owner removes, then rotates. A removed member who is still connected can push under the old
epoch until the rotation lands; that window is the time between the two requests.

### Mounts (client-defined)

A user's root space index doc also has a `Y.Map` named `mounts`: `space_id → Y.Map{path}`, the vault
folder each share is mounted at. Every device of that user mounts the same shares at the same
paths. The root space's mirror skips everything under a mount.

**Converting a folder** (owner): in one index transaction, add the mount and tombstone every root
entry under the folder. Other devices then stop syncing those paths in the root space without
deleting the files (tombstones for paths now inside a mount only drop the baseline). The share's
own mirror then imports the files on disk. Root-space history for those files stays in the root space.

**Leaving or being removed**: the mount is removed. Files stay on disk and the root space imports
them as ordinary private files.

**Moving the mount folder** moves the mount (all devices follow). **Deleting the mount folder**
unmounts the share on this user's devices; it does not delete the share's files for other members.

### Member profiles (client-defined)

A share's index doc has a `Y.Map` named `members`: `sign_pk b64u → JSON string {name, color,
avatar?}`, written by each member for themselves (viewers can't write, so they stay unnamed).
`avatar` is a small JPEG data URL (64 px, ≤ 24 000 chars). It names cursors and the member list.
Awareness `user` carries `pk` (the sign_pk, b64u) so cursors can look the profile up. A user's own
root (or profile) space has the same map with just their own `{avatar}`, so their devices share it.
(Not a security boundary: any member can write any key. Signed membership is future work.)

### Key commitments (client-defined)

Wrapped keys come from the host, and sealed boxes are anonymous, so clients don't take a key's
word for itself. A space's index doc has a `Y.Map` named `keys`: `epoch → JSON {fp, by, sig}`, where
`fp = b64u(BLAKE2b-256(key="tezca-key-fp", space_key))` and `sig` is `by`'s Ed25519 signature over
`sigInput("key-commit", space_id, u32(epoch), fp)`. Clients encrypt only with keys they trust:

- ROOT/PROFILE spaces: committed by the user's own identity.
- SHARE spaces: committed by an owner the device already trusts: owners present when it first
  opened the share, plus owners vouched for in the index's `owners` map (`sign_pk b64u → {by,
  sig}` over `sigInput("owner", space_id, owner)`) by a trusted owner; keys received through an
  invite are trusted directly (the invite secret authenticates them).
- Keys a device held before commitments existed (trust on first use, up to the epoch current then).

Untrusted keys are used only to read, and are replaced if the host later offers a different key
for that epoch. Owners commit new keys when they rotate, and devices commit trusted keys that lack a
commitment. After a doc has integrated an update under epoch N, updates under older epochs are
refused.

### Recommended plugins (client-defined)

A share's index doc has a `Y.Map` named `plugins`: `community plugin id → JSON string {name,
author?}`, written by members who can edit. Clients offer to install them (from Obsidian's community
plugin directory, through Obsidian's installer) when someone joins the share.

## Cross-host shares and guests (M4)

### Guests

A **guest** is a host user (`HostRole.GUEST`) who exists only to reach the spaces they're invited
to. Redeeming a share invite on a host where the caller has no account creates a guest account:

`POST /api/share-invites/redeem` also accepts an unregistered caller. Instead of an HTTP signature,
the body then carries `{token, sign_pk, box_pk, sig}` with
`sig = sign(sigInput("redeem", server_id, token, sign_pk, box_pk))` (exactly like `/api/redeem`).
The server creates the user with role GUEST, then redeems as before. A registered caller may use
either form. Host invites (`/api/invites`) are unaffected and still make MEMBERs.

Guests:
- can't create spaces, except **one** space of kind `PROFILE` (a second one is `CONFLICT`);
- can do everything a member of a space can within the spaces they belong to (their role there
  still applies);
- can create pairings (to add their own devices);
- have a storage quota of `TEZCA_GUEST_QUOTA_MB` (default 1024; 0 = unlimited). It counts the
  blobs they uploaded on this host plus the retained updates and snapshots they authored, in any
  space (their PROFILE space and the shares where they're an editor). Updates and snapshots that
  the history policy prunes stop counting, so usage goes down again over time. A blob upload over
  it gets 507 with `{"error":"guest storage quota exceeded"}`; a `PushUpdate` or `PutSnapshot`
  over it gets `Error{TOO_LARGE, "guest storage quota exceeded"}` and isn't stored. Blobs that
  already exist (dedup) don't count again.

`GET /api/info` adds `role` when the request carries a valid HTTP signature (`"admin"`, `"member"`,
`"guest"`), so a client can tell how a host sees it.

### Profile space (client-defined)

A user with no host of their own (a "hostless" guest) keeps their mount table in a `PROFILE` space
on the first host that invited them, in the same `mounts` map a root space uses. That space never
holds vault files. Its host is the one their devices pair through.

### Multiple hosts

A client keeps one connection per host it has spaces on. A mount records the host of a share that
isn't on the root/profile space's host: `mounts[space_id] = {path, host?}` (`host` absent = the
root host). Space IDs are random 128-bit values, so they don't collide across hosts; clients still
key spaces by `(host, space_id)`.

A user who has their own host and joins a share on another host becomes a guest there (unless
they're already a user), and mounts it with `host` set.

## Index document (client-defined, opaque to the server)

The `index` doc of a space is a `Y.Map` named `files`: `file_id → Y.Map` with `path` (space-relative),
`kind` (`md` | `canvas` | `folder` | `blob`), `deleted`, `ctime`, `mtime`. A `md` entry's content is the
doc `file_id` (`Y.Text` "content"). A `canvas` entry's content is the doc `file_id` too, as a `Y.Map`
"canvas" holding `nodes` and `edges` (`Y.Map` of id → `Y.Map` of fields, card text as `Y.Text`),
`nodeOrder`/`edgeOrder` (`Y.Array` of ids) and `extra` (other top-level JSON keys). Clients that don't know a
kind ignore the entry. Files under the vault's config folder (`.obsidian/…`) appear only in a root space,
as `blob` entries, for the categories each device opted into. A `blob` entry also has `blob` = JSON `{id, epoch, size, hash}` (`hash` is an unkeyed
BLAKE2b-128 hex of the plaintext, for local change detection) or is absent while the first upload is
pending, and `prev` = JSON array of up to 20 earlier `blob` values (newest first), its version history.

## Pairing payload (plugin-defined, opaque to the server)

`ciphertext = nonce(24) ‖ xchacha20poly1305(JSON{seed, host, space_id, display_name}, AD = sigInput("ad-pairing"), key = BLAKE2b-256(key = secret, msg = "tezca/v1/pairing"))`

The `secret` is 32 random bytes that travel only in the deep link (`k=`).
